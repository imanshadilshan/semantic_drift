- **Day 16-19 — Mitigation strategies**: `src/mitigation.py` implemented.
  - `region_locking(pre_image, instruction)`: runs the edit on the full image as normal (unchanged behavior), then reverts every pixel outside the target region's SAM box back to the pre-edit image — post-hoc correction.
  - `masked_conditioning(pre_image, instruction, padding=32)`: crops down to just the target region *before* generation (with padding for context), runs the edit only on that crop, pastes it back — the model never sees the rest of the image, a stricter generation-time constraint than region_locking. Expected to show boundary seams (H2).
  - Both identify the target region with the exact same SAM+CLIP procedure `drift_score.py`'s scoring uses, so mitigation and measurement agree on what "the target" means.
  - `src/edit_runner.py`'s `run_edit_chain()` mitigation hook was redesigned: the old `mitigation(pre_image, raw_edited_image) -> corrected_image` signature only supported post-hoc correction, which can't express masked_conditioning (needs to control what the model is given, not just clean up after). New signature is `step_fn(pre_image, instruction) -> edited_image`, a full replacement for the per-step generation call, defaulting to plain `run_edit`. No other call site was affected (only the baseline notebook cell called it, without the optional argument).
  - `src/drift_pipeline.py` extracted from `compute_baseline_drift.py` (which had the SAM+CLIP+scoring+resilience+resume logic that now needs to run 3 times — baseline, region_locking, masked_conditioning — rather than duplicating ~130 lines 3 ways). `scripts/compute_baseline_drift.py` is now a thin wrapper; `scripts/compute_mitigated_drift.py <strategy>` is the equivalent for either mitigation strategy.
  - Both mitigation functions verified locally with mocked SAM/CLIP/model calls and solid-color test images — confirmed pixel-exact box boundaries and correct padding-clamp behavior near image edges (no real GPU needed for this, it's pure compositing logic). Added as permanent tests in `tests/test_mitigation.py` (14/14 total tests passing).

  - **Real bug hit on first Colab run**: `region_locking` crashed with `TypeError: 'float' object cannot be interpreted as an integer` inside `PIL.Image.paste()`. Root cause: SAM's own `mask["bbox"]` values are Python floats (from a tensor `.tolist()`), not ints — `Image.crop()` silently tolerates floats, but `paste()` does not. `get_region_boxes()` only ever fed `crop()` before (baseline scoring), so this was latent until mitigation.py's `paste()` calls exercised it for the first time against real SAM output. My local mock-based tests used plain int tuples as stand-ins for SAM's boxes, so they didn't catch this either — worth remembering that mocks are only as good as how faithfully they match the real thing's actual return types. Fixed at the source in `get_region_boxes()` (round + cast to int once, rather than patching every call site that eventually pastes), with two new regression tests in `tests/test_segment.py` that mock SAM's generator to return float bboxes specifically, so this exact bug class can't silently return (16/16 tests passing).
  - **Second Colab run completed cleanly, 120/120 chains for both strategies, 0 skipped steps.** Headline result: mean cumulative drift is baseline 0.293 → region_locking 0.039 (86.8% reduction) → masked_conditioning 0.085 (71.1% reduction). Both are large, real reductions — H3/RQ3 looks strongly supported pending the actual paired significance test.
  - **Colab's `files.download()` gave all three CSVs the same misleading filename** (`baseline_drift_scores (1/2/3).csv`) when called in a loop — identified the real content of each by their cumulative-score means (0.293 / 0.092 / 0.032) rather than trusting filenames, and placed them correctly as `baseline_drift_scores.csv` (confirmed byte-identical in content to the already-committed one — safe duplicate), `masked_conditioning_drift_scores.csv`, and `region_locking_drift_scores.csv`.
  - **Visual spot-check on the baseline "hero example" chain (000000407298, baseball glove, baseline cumulative 0.565) confirms the numbers are real, and surfaced a genuine, well-diagnosed limitation.** `region_locking` (0.076) preserves the boy's face/shirt/background almost perfectly, with one visible "seam" artifact (a stray yellow rectangle near the glove) — a real instance of the boundary cost H2 predicted. `masked_conditioning` (0.180) handled steps 1-3 well — even a fully-degenerate edit (step 3 turned solid black) stayed contained to a small patch, exactly as designed — but step 4 ("add a cap on the boy's head") produced an entirely different, unrelated two-people scene. Traced the cause directly: re-ran `_target_box()` on that exact image+instruction and found the identified target box was **(0, 0, 511, 511) — 99.6% of the frame**. This is the already-documented "add instruction" limitation (CLIP has nothing existing to match "a cap" against) manifesting concretely: when the top-1 target region degenerates to near-whole-image, `masked_conditioning`'s crop provides no real spatial constraint at all — same exposure `region_locking` has for a giant box. `region_locking` came out fine on this particular step most likely because diffusion sampling is stochastic (no fixed seed) — its full-image call and `masked_conditioning`'s near-full-image crop call are two independent random draws from the same model, and one landed conservative while the other didn't. **Conclusion worth stating plainly in the write-up's Limitations section: both mitigations are only as good as target-region identification, and that step has a known, reproducible weak spot for "add" instructions** — not a flaw specific to either mitigation's mechanism.
